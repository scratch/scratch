## Quick Start

Scratch requires no configuration so it's easy to get started. First, install:

```bash
# Install scratch
curl -fsSL https://scratch.dev/install.sh | bash
```

Then create a project and start the dev server:

```bash
# Create a new project
scratch create

# Start the dev server
scratch dev
```

Now you're ready to start writing in `pages/index.mdx`. Use the `publish` command to share with specific people, your team, or the world:

```bash
# Publish with a Scratch Server on Cloudflare
# Grant access to specific people, @youdomain.com, or the world
scratch publish
```

## Project Structure

Scratch uses an opinionated project structure that makes it easy to focus on your content:

<Files>
```
my-site/
  pages/                   # Markdown pages and components
    posts/ (collapsed)
      hello.md             # accessible at /posts/hello/
      world.md             # accessible at /posts/world/
    index.mdx              # accessible at /
    about.mdx              # accessible at /about/
    Counter.tsx            # auto-imported in MDX files
  public/ (collapsed)      # Static assets (copied to dist/)
    favicon.svg
    robots.txt
  src/ (collapsed)         # Global styles and components
    markdown/ (collapsed)  # Override default markdown elements
      index.ts
      CodeBlock.tsx
      Heading.tsx
      Link.tsx
    template/ (collapsed)  # Page layout components
      PageWrapper.jsx      # Wraps every page
      Header.jsx
      Footer.jsx
    tailwind.css           # Global styles
  .scratch/ (collapsed)    # Project configuration
    project.toml           # Server and publish settings
  package.json             # Dependencies
  .gitignore
```
</Files>

### pages/

Markdown files live in `pages/` and can be MDX (`.mdx`) or vanilla Markdown (`.md`). Scratch compiles each file into a static page:

| File | URL |
|------|-----|
| `pages/index.mdx` | `/` |
| `pages/about.mdx` | `/about/` |
| `pages/posts/index.mdx` | `/posts/` |
| `pages/posts/hello.mdx` | `/posts/hello/` |

**Components** can live in `pages/` or `src/`. Components are auto-detected by filename and imported during the build process. A `Counter` component defined in `Counter.tsx` is available as `<Counter />` in any MDX file.

**Static assets** like images can also live in `pages/`. They're copied to the output directory and served at the same path.

### src/

The `src/` directory contains global styles and components:

- `src/tailwind.css` — Global CSS with Tailwind
- `src/template/PageWrapper.jsx` — Wraps all pages (headers, footers, nav)
- `src/template/` — Layout components (Header, Footer, etc.)
- `src/markdown/` — Override default markdown rendering

### public/

Static files like favicons, `robots.txt`, or `_redirects` go in `public/`. These are copied directly to `dist/`.

### .scratch/

Project configuration lives in `.scratch/project.toml`. This file is created when you first run `scratch publish` or `scratch config`.

### package.json

Scratch automatically installs build dependencies. Add your own dependencies by editing `package.json`.

## Writing Content

### Markdown Basics

Scratch supports [CommonMark](https://commonmark.org/) and [GitHub Flavored Markdown](https://github.github.com/gfm/) (tables, strikethrough, task lists, autolinks).

```markdown
# Heading 1
## Heading 2

**Bold** and *italic* text.

- List item
- [x] Task list item

| Column 1 | Column 2 |
|----------|----------|
| Cell     | Cell     |

[Link](https://example.com) and `inline code`.
```


### Code

Scratch uses [Tailwind Typography](https://github.com/tailwindlabs/tailwindcss-typography) to render your prose with a clean aesthetic.

 It supports [Github-flavored Markdown](https://github.com/remarkjs/remark-gfm) out of the box. Code blocks use syntax highlighting by [Shiki](https://shiki.style/).

```python
def greet(name: str) -> str:
    return f"Hello, {name}!"

print(greet("World"))
```

### Using Components

Scratch uses [MDX](https://mdxjs.com) to render JSX in your Markdown content:

```mdx
# My Page

Here's a counter: 

<Counter />

and here's a button:

<Button>Click me</Button>
```

Components can live in `pages/` or `src/`. A `Counter` component defined in `Counter.tsx` is available as `<Counter />` in any MDX file and does not need to be explicitly imported.

### Component Patterns

**Self-closing components** embedded in MDX files are wrapped in a `not-prose` div automatically during the build process in order to isolate them from the [Tailwind Typography](https://github.com/tailwindlabs/tailwindcss-typography) styling used to render Markdown:
```mdx
<Chart />
```

**inline children** inherit [Tailwind Typography](https://github.com/tailwindlabs/tailwindcss-typography) styles:
```mdx
<Button>Click me</Button>
```

**Block children** are converted to markdown when there are blank lines between the component tags and the content:
```mdx
<Callout>

## Warning

This is **markdown** inside a component.

</Callout>
```

### Static Assets

Images and other assets can live in `pages/` or `public/`:

```mdx
![My image](./image.png)

![From public](/logo.svg)
```

Relative paths are resolved during the Scratch build process and work correctly at any base path.

## Styling

### Tailwind CSS

Scratch uses [Tailwind CSS](https://tailwindcss.com/) v4. Edit `src/tailwind.css` to customize global styles:

```css
@import 'tailwindcss';
@plugin "@tailwindcss/typography";

/* Custom styles */
.prose a {
  @apply text-blue-600 hover:text-blue-800;
}
```

### Typography

Markdown content is styled with [Tailwind Typography](https://github.com/tailwindlabs/tailwindcss-typography). Configure in `src/template/PageWrapper.jsx`:

```jsx
<div className="prose prose-lg prose-slate">
  {children}
</div>
```

### Excluding from Prose

Use `not-prose` to exclude elements from typography styling:

```jsx
<div className="not-prose">
  <CustomComponent />
</div>
```

Scratch automatically wraps self-closing components in `not-prose` divs.

### Custom Markdown Components

Override default markdown elements by creating components in `src/markdown/`:

```tsx
// src/markdown/Link.tsx
export default function Link({ href, children, ...props }) {
  const isExternal = href?.startsWith('http');
  return (
    <a
      href={href}
      target={isExternal ? '_blank' : undefined}
      rel={isExternal ? 'noopener noreferrer' : undefined}
      {...props}
    >
      {children}
    </a>
  );
}
```

Export from `src/markdown/index.ts`:

```ts
export { default as a } from './Link';
export { default as pre } from './CodeBlock';
export { default as h1, default as h2 } from './Heading';
```

### PageWrapper

The `PageWrapper.jsx` component is exactly what it sounds like: a default wrapper for every markdown page. It's used to set global styles and insert header and footer components (which are also also defined in `src/template/`). Changes you make to this component will affect every page in your project.

## Commands

### scratch create

Create a new Scratch project.

```bash
scratch create [path]
```

| Option | Description |
|--------|-------------|
| `--no-src` | Skip the `src/` template directory |
| `--no-package` | Skip `package.json` template |
| `--minimal` | Skip example content |

**Example:**
```bash
scratch create my-blog
scratch create docs --minimal
```

### scratch dev

Start the development server with hot module reloading.

```bash
scratch dev [path]
```

| Option | Default | Description |
|--------|---------|-------------|
| `-p, --port <port>` | `5173` | Server port |
| `-n, --no-open` | — | Don't open browser |
| `-d, --development` | — | Unminified output with source maps |
| `-b, --base <path>` | `/` | Base path for deployment |
| `--static <mode>` | `assets` | Static file handling (see below) |
| `--strict` | — | Disable auto-injection of imports |
| `--highlight <mode>` | `auto` | Syntax highlighting mode |

**Static modes:**
- `public` — Only serve files from `public/`
- `assets` — Serve images and media from `pages/`, but not JS/TS files
- `all` — Serve all static files including code

**Highlight modes:**
- `off` — No syntax highlighting
- `popular` — Common languages only
- `auto` — Detect from code blocks (default)
- `all` — All languages

| `--no-ssg` | — | Disable static site generation |
| `--static <mode>` | `assets` | Static file handling |
| `--strict` | — | Disable auto-injection |
| `--highlight <mode>` | `auto` | Syntax highlighting mode |

**Example:**

## Authentication

You can use Scratch to publish your projects to [app.scratch.dev](https://app.scratch.dev) or a self-hosted server.

### scratch login

Log in to a Scratch server.

```bash
scratch login [server-url]
```

| Option | Default | Description |
|--------|---------|-------------|
| `--timeout <minutes>` | `10` | Timeout for login approval |

**How it works:**
1. CLI displays a verification code
2. Browser opens to the login page
3. Sign in and approve the device
4. CLI receives a token and saves it

```bash

https://app.scratch.dev/device?user_code=ABCD-1234
```

### scratch logout

```bash

```

Clears saved credentials for the specified server.

## Publishing Your Site

### scratch publish

Build and deploy your project.

```bash
scratch publish [path]
```

| Option | Description |
|--------|-------------|
| `--server <url>` | Server URL (uses config or prompts) |
| `--name <name>` | Override project name |
| `--visibility <v>` | Override visibility setting |
| `--no-build` | Skip build step (deploy existing `dist/`) |
| `--dry-run` | Show what would be deployed |

**Example:**
```bash
scratch publish
scratch publish --visibility private
scratch publish --name my-docs --server https://my-server.com
```

**First publish flow:**
1. Prompts for project name if not configured
2. Prompts for visibility setting
3. Builds the project
4. Uploads to server
5. Opens the deployed URL

### Project Naming

Project names must be:
- 3-63 characters long
- Lowercase letters, numbers, and hyphens only
- Start with a letter

Reserved names: `api`, `auth`, `admin`, `www`, `app`, `help`, `support`, `static`, `assets`, `cdn`, `files`, `upload`, `download`

### URL Structure

Your published site URL is:

```
https://pages.scratch.dev/<username>/<project-name>/
```

For example, if your email is `pete@example.com` and project is `my-blog`:
```
https://pages.scratch.dev/pete@example.com/my-blog/
```

On single-domain deployments, the URL uses just the local part:
```
https://pages.scratch.dev/pete/my-blog/
```

### Updating Your Site

Run `scratch publish` again to deploy updates. Each deploy creates a new version and immediately becomes live.

## Visibility

Control who can access your published site.

### Visibility Modes

| Mode | Description |
|------|-------------|
| `public` | Anyone can access |
| `private` | Only you can access |
| `@domain.com` | Anyone with email at that domain |
| `user@example.com` | Specific email address |
| `a@x.com,b@y.com` | Multiple addresses (comma-separated) |

**Examples:**
```bash
# Public site
scratch publish --visibility public

# Private site (only you)
scratch publish --visibility private

# Team access by domain
scratch publish --visibility @mycompany.com

# Specific people
scratch publish --visibility "alice@x.com,bob@y.com"

# Mix domains and emails
scratch publish --visibility "@mycompany.com,contractor@gmail.com"
```

### Setting Visibility

Set visibility when publishing:
```bash
scratch publish --visibility private
```

Or configure it in `.scratch/project.toml`:
```toml
[project]
name = "my-blog"
visibility = "private"
```

Or run the interactive config:
```bash
scratch config
```

When someone without access visits a private site, they're prompted to sign in. If they still don't have access, they see a 403 error.

## Build Pipeline

When you run `scratch build`, Scratch compiles your MDX files into a **fully static website**—pre-rendered HTML, CSS, and JavaScript that can be hosted anywhere.

### Build Steps

1. **Dependency Resolution** — Auto-install npm dependencies from `package.json`
2. **Entry Generation** — Generate client/server entry files for each page
3. **MDX Compilation** — Process markdown through remark/rehype plugins
4. **Tailwind Compilation** — Compile CSS with only used utilities
5. **Server Build** — Build server bundle for pre-rendering
6. **Client Build** — Bundle client JavaScript with minification
7. **HTML Generation** — Render static HTML with meta tags
8. **Static Assets** — Copy files from `public/`
9. **Output** — Write to `dist/`

### MDX Plugins

**Remark plugins** (Markdown AST):
- **remark-gfm** — Tables, strikethrough, task lists
- **remark-frontmatter** — YAML metadata extraction
- **remark-auto-import** — Auto-import components
- **remark-not-prose** — Wrap components in `not-prose`

**Rehype plugins** (HTML AST):
- **rehype-raw** — Allow raw HTML in markdown
- **rehype-image-paths** — Transform relative image paths
- **rehype-shiki** — Syntax highlighting
- **rehype-footnotes** — Position footnotes correctly

### Syntax Highlighting

Code blocks are highlighted with [Shiki](https://shiki.style/). Control with `--highlight`:

```bash
scratch build --highlight popular  # Common languages only
scratch build --highlight all      # All languages
scratch build --highlight off      # No highlighting
```

### Cache Management

Build cache lives in `.scratch/cache/`. Clear it with:

```bash
scratch clean
```

## Self-Hosting

You can run your own Scratch server instead of using app.scratch.dev.

### When to Self-Host

**Use app.scratch.dev when:**
- You want zero infrastructure management
- Public or personal private sites
- Standard authentication (Google OAuth)

**Self-host when:**
- You need enterprise SSO (Cloudflare Access)
- Data must stay on your infrastructure
- Custom domain requirements
- Organization-wide deployment

### Infrastructure Requirements

A Scratch server runs on Cloudflare:
- **Workers** — Server code
- **D1** — SQLite database
- **R2** — File storage

### Setup

1. Clone the repository:
```bash
git clone https://github.com/scratch/scratch
cd scratch
```

2. Run the setup wizard:
```bash
bun ops server -i prod setup
```

This creates:
- `server/.prod.vars` — Environment variables
- `server/wrangler.prod.toml` — Cloudflare config

3. Configure required variables in `.prod.vars`:

```bash
# Domain configuration
BASE_DOMAIN=scratch.example.com
APP_SUBDOMAIN=app
CONTENT_SUBDOMAIN=pages

# Authentication
BETTER_AUTH_SECRET=<random-string>
AUTH_MODE=better-auth
GOOGLE_CLIENT_ID=<from-google-console>
GOOGLE_CLIENT_SECRET=<from-google-console>

# Access control
ALLOWED_USERS=@yourcompany.com
MAX_VISIBILITY=@yourcompany.com

# Resource IDs (from Cloudflare dashboard)
D1_DATABASE_ID=<your-d1-id>
```

4. Push secrets and deploy:
```bash
bun ops server -i prod config push
bun ops server -i prod db migrate
bun ops server -i prod deploy
```

### Environment Variables

| Variable | Description |
|----------|-------------|
| `BASE_DOMAIN` | Base domain (e.g., `scratch.example.com`) |
| `APP_SUBDOMAIN` | App subdomain (e.g., `app`) |
| `CONTENT_SUBDOMAIN` | Content subdomain (e.g., `pages`) |
| `BETTER_AUTH_SECRET` | Session encryption key |
| `AUTH_MODE` | `better-auth` or `cloudflare-access` |
| `GOOGLE_CLIENT_ID` | Google OAuth client ID |
| `GOOGLE_CLIENT_SECRET` | Google OAuth client secret |
| `ALLOWED_USERS` | Who can create accounts (`*`, `@domain.com`, or emails) |
| `MAX_VISIBILITY` | Maximum visibility for projects |
| `D1_DATABASE_ID` | Cloudflare D1 database ID |

### Authentication Modes

**BetterAuth (default)** — Google OAuth
- Users sign in with Google
- Sessions stored in D1 database
- Good for public or semi-public deployments

**Cloudflare Access** — Enterprise SSO
- Authentication handled at Cloudflare edge
- Supports SAML, OIDC, Okta, Azure AD, etc.
- Server validates Cloudflare JWT
- Good for corporate deployments

To use Cloudflare Access:
```bash
AUTH_MODE=cloudflare-access
CF_ACCESS_TEAM_NAME=your-team
CF_ACCESS_AUD=<application-aud>
```

### Domain Configuration

Scratch uses two subdomains for security:

- **App subdomain** (`app.scratch.dev`) — API, authentication, dashboard
- **Content subdomain** (`pages.scratch.dev`) — User-uploaded content

This separation prevents malicious uploaded JavaScript from stealing session cookies.

## Cloudflare Access

For servers behind Cloudflare Access, configure service tokens in the CLI.

### scratch cf-access

Configure Cloudflare Access credentials.

```bash
scratch cf-access [server-url]
```

Prompts for:
- **Client ID** — From Cloudflare Access service token
- **Client Secret** — From Cloudflare Access service token

These credentials are sent with API requests to pass through Cloudflare Access.

**When to use:** Only needed for self-hosted servers using Cloudflare Access authentication mode.

## API Reference

The Scratch server exposes a REST API for programmatic access.

### Authentication

API requests use Bearer token authentication:

```bash
curl -H "Authorization: Bearer <token>" \
  https://app.scratch.dev/api/me
```

Get your token from `~/.scratch/credentials.json` after running `scratch login`.

### Endpoints

#### User

**GET /api/me** — Get current user
```json
{
  "user": {
    "id": "abc123",
    "email": "you@example.com",
    "name": "Your Name",
    "image": null
  }
}
```

#### Projects

**GET /api/projects** — List your projects
```json
{
  "projects": [
    {
      "id": "abc123",
      "name": "my-blog",
      "owner_id": "user123",
      "visibility": "public",
      "live_version": 3,
      "deploy_count": 3,
      "urls": {
        "primary": "https://pages.scratch.dev/pete/my-blog/",
        "byId": "https://pages.scratch.dev/user123/my-blog/"
      },
      "created_at": "2025-01-15T...",
      "updated_at": "2025-01-20T...",
      "last_deploy_at": "2025-01-20T..."
    }
  ]
}
```

**GET /api/projects/:name** — Get project details

**POST /api/projects** — Create a project
```bash
curl -X POST \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"name": "my-project"}' \
  https://app.scratch.dev/api/projects
```

**PATCH /api/projects/:name** — Update project
```bash
curl -X PATCH \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"visibility": "private"}' \
  https://app.scratch.dev/api/projects/my-blog
```

**DELETE /api/projects/:name** — Delete project

#### Deploys

**POST /api/projects/:name/deploy** — Deploy a project
```bash
curl -X POST \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/zip" \
  --data-binary @dist.zip \
  "https://app.scratch.dev/api/projects/my-blog/deploy?visibility=public"
```

Query parameters:
- `visibility` — Set project visibility
- `project_id` — Local project ID (for rename detection)

#### Share Tokens

**GET /api/projects/:name/share-tokens** — List share tokens

**POST /api/projects/:name/share-tokens** — Create share token
```bash
curl -X POST \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"name": "Client review", "duration": "1w"}' \
  https://app.scratch.dev/api/projects/my-blog/share-tokens
```

**DELETE /api/projects/:name/share-tokens/:id** — Revoke share token

### Error Codes

| Code | Description |
|------|-------------|
| `PROJECT_NAME_INVALID` | Invalid project name format |
| `PROJECT_NAME_TAKEN` | You already have a project with this name |
| `PROJECT_NOT_FOUND` | Project doesn't exist or you don't own it |
| `VISIBILITY_INVALID` | Invalid visibility format |
| `VISIBILITY_EXCEEDS_MAX` | Visibility exceeds server maximum |
| `INVALID_ZIP` | Upload is not a valid zip file |
| `DEPLOY_TOO_LARGE` | Zip file exceeds size limit |
| `TOO_MANY_FILES` | Deploy has too many files |
| `SHARE_TOKEN_NOT_FOUND` | Share token doesn't exist |
| `SHARE_TOKEN_LIMIT_EXCEEDED` | Too many active share tokens |

## Troubleshooting

### Build Errors

**"Cannot find module"**
- Run `scratch clean` then try again
- Check `package.json` for missing dependencies
- Run `bun install` manually

**"Component not found"**
- Ensure filename matches component name (`Button.tsx` → `<Button />`)
- Check for typos in component name
- Verify file is in `pages/` or `src/`

**Syntax highlighting not working**
- Try `--highlight all` to include all languages
- Check language identifier in code fence matches Shiki

### Login Issues

**"Device authorization timed out"**
- Increase timeout: `scratch login --timeout 20`
- Check browser opened to correct URL
- Verify you approved the correct code

**"Not authenticated" on publish**
- Run `scratch whoami` to check login status
- Run `scratch login` to re-authenticate
- Check `~/.scratch/credentials.json` exists

### Publish Failures

**"Project name is reserved"**
- Choose a different name (avoid `api`, `auth`, etc.)

**"Visibility exceeds server maximum"**
- Server restricts visibility options
- Use `private` or allowed domain

**"Deploy too large"**
- Remove large files from `dist/`
- Check for accidentally included `node_modules`
- Use `.gitignore` patterns

### Debugging

Use verbose mode to see detailed output:

```bash
scratch dev -v
scratch build -v
scratch publish -v
```

For Bun-specific errors:

```bash
scratch build --show-bun-errors
```
